# ESAS: Обзор Системы

## Что это за проект

ESAS — это экосистема из двух Telegram-ботов и фонового sync-сервиса:

- `client_bot`: клиент оформляет и сопровождает заявку.
- `partner_bot`: сервисный центр регистрируется, проходит модерацию и работает с заявками.
- `sync_service`: синхронизирует данные с Google Sheets и обратно.

## Архитектура на уровне доменов

- **Каталог**: бренды, модели, категории, метро.
- **Сервисы**:
    - `Service` — финальный профиль, который участвует в ранжировании и заказах.
    - `ServiceDraft` — рабочая анкета партнёра и статус модерации.
    - `ServiceBankDetails` — банковские реквизиты (отдельная таблица).
    - `ServiceOwnerSettings` — настройки уведомлений владельца.
- **Заказы**: полный жизненный цикл клиента и партнёра (`awaiting_payment -> ... -> completed / disputed / ...`) с централизованными переходами статусов через `order_lifecycle`.
- **Политики и интеграции**:
    - `payment_policy` — единый расчёт предоплаты/остатка и валидация диапазонов гидроизоляции.
    - `notifications` — отправка уведомлений с retry/backoff и dedupe-ключами.

## Ключевые процессы

1. Клиент заполняет форму в режиме city-first: сначала город, затем (для Москвы) метро или (для других городов) адрес.
2. Для не-Москвы адрес клиента геокодируется через Яндекс Геокодер и участвует в подборе сервиса по расстоянию.
3. Партнёр заполняет анкету тоже в режиме city-first: для Москвы обязательны метро+адрес, для других городов метро не запрашивается.
4. Перед отправкой анкеты партнёра валидируются координаты сервиса; если геокодер не вернул координаты, отправка блокируется.
5. Активный партнёр редактирует профиль через тот же draft-FSM, что и при первичном заполнении (единая валидация и зависимости полей).
6. Администратор модерирует партнёров и контролирует поток заявок.
7. Google Sheets остаётся внешним операционным интерфейсом для сервисов/отчётности.
8. Бизнес-метрики сервисов выгружаются в отдельный лист Google Sheets (`Метрики сервисов`).

## Точки запуска

- `python -m client_bot`
- `python -m partner_bot`
- `python -m sync_service`

## Источники конфигурации

- `config.yaml`: инфраструктура и бизнес-параметры (DB, Redis, календарь, листы, интервалы).
- `.env`: секреты и токены (`CLIENT_BOT_TOKEN`, `PARTNER_BOT_TOKEN`, `YANDEX_GEOCODER_API_KEY`, при необходимости `GOOGLE_SHEET_ID`).

## Что важно для сопровождения

- Проект живёт в split-модели: анкета партнёра больше не является частью `Service`.
- Редактирование активного профиля не переводит сервис в ремодерацию: `Service.partnership_status` и `ServiceDraft.status` остаются `активный`.
- После каждого редактирования активного профиля админы получают уведомление об изменённом поле.
- Sheets-синк работает по **ID сервиса**, не по имени.
- Inbound Sheets-синк устойчив к «грязным» строкам: невалидные значения дают warning + fallback, проблемные строки пропускаются без падения процесса.
- Изменения из Sheets зеркалируются не только в `Service`, но и в связанный `ServiceDraft` (включая банковские поля), чтобы UI ботов показывал актуальные данные.
- Каждый переход статуса заказа пишется в `order_status_history` (кто/откуда/куда/почему).
- `sync_service` на старте делает `dry_run` health-check интеграций перед боевым initial sync.
- Логирование работает в файловом режиме с ротацией: отдельные файлы для обычных и бизнес-логов каждого сервиса.
- Все входные текстовые шаги проходят Pydantic-валидацию.
- Все критические пользовательские действия логируются в `user_actions`.
- Для не-Москвы подбор сервиса выполняется по евклидовой дистанции с ограничением по `matching.max_distance_km`.
