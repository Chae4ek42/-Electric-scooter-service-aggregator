# ESAS: Обзор Системы

## Что это за проект

ESAS — это экосистема из двух Telegram-ботов и фонового sync-сервиса:

- `client_bot`: клиент оформляет и сопровождает заявку.
- `partner_bot`: сервисный центр регистрируется, проходит модерацию и работает с заявками.
- `sync_service`: синхронизирует данные с Google Sheets и обратно.

## Архитектура на уровне доменов

- **Каталог**: бренды, модели, категории, метро.
- **Сервисы**:
    - `Service` — финальный профиль, который участвует в ранжировании и заказах.
    - `ServiceDraft` — рабочая анкета партнёра и статус модерации.
    - `ServiceBankDetails` — банковские реквизиты (отдельная таблица).
    - `ServiceOwnerSettings` — настройки уведомлений владельца.
- **Заказы**: полный жизненный цикл клиента и партнёра (`awaiting_payment -> ... -> completed / disputed / ...`) с централизованными переходами статусов через `order_lifecycle`.
- **Политики и интеграции**:
    - `payment_policy` — единый расчёт предоплаты/остатка и валидация диапазонов гидроизоляции.
    - `notifications` — отправка уведомлений с retry/backoff и dedupe-ключами.

## Ключевые процессы

1. Клиент заполняет форму -> сервис подбирается автоматически после выбора времени.
2. Партнёр подтверждает заявку, формирует смету, обновляет цену при необходимости.
3. Администратор модерирует партнёров и контролирует поток заявок.
4. Google Sheets остаётся внешним операционным интерфейсом для сервисов/отчётности.

## Точки запуска

- `python -m client_bot`
- `python -m partner_bot`
- `python -m sync_service`

## Источники конфигурации

- `config.yaml`: инфраструктура и бизнес-параметры (DB, Redis, календарь, листы, интервалы).
- `.env`: секреты и токены (`CLIENT_BOT_TOKEN`, `PARTNER_BOT_TOKEN`, при необходимости `GOOGLE_SHEET_ID`).

## Что важно для сопровождения

- Проект живёт в split-модели: анкета партнёра больше не является частью `Service`.
- Sheets-синк работает по **ID сервиса**, не по имени.
- Каждый переход статуса заказа пишется в `order_status_history` (кто/откуда/куда/почему).
- `sync_service` на старте делает `dry_run` health-check интеграций перед боевым initial sync.
- Все входные текстовые шаги проходят Pydantic-валидацию.
- Все критические пользовательские действия логируются в `user_actions`.
