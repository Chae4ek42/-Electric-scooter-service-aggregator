# Service Matching Pipeline

## Где начинается подбор

Подбор запускается в клиентском потоке после выбора времени (`calendar_time`).

## Что влияет на стратегию

- Город клиента (`user_city`) определяет алгоритм подбора:
    - Москва: метро-логика (как раньше).
    - Не Москва: подбор по расстоянию между координатами клиента и сервиса.
- Для не-Москвы клиентский адрес предварительно геокодируется через Яндекс Геокодер (retry + fallback-варианты запроса).
- Если координаты не удалось получить, подбор не продолжается: бот запрашивает более точный адрес (улица/дом/корпус).
- Для не-Москвы сервис должен иметь координаты в профиле.

## Pipeline

1. Формируется `RankingContext` из FSM.
2. `rank_services()` отбирает подходящие сервисы с учетом `user_city`.
3. Если найден матч:
    - в FSM записывается `service_id`,
    - пользователю показывается подтверждение заявки.
4. Если матчей нет:
    - создается заказ со статусом `no_center`,
    - пользователь получает понятное сообщение.

## Алгоритм для не-Москвы

1. Из контекста берутся координаты клиента (`user_latitude`, `user_longitude`).
2. Для каждого кандидата вычисляется евклидова дистанция (км) до сервиса.
3. Кандидаты дальше `matching.max_distance_km` отбрасываются.
4. Оставшиеся сортируются по расстоянию (ближе -> выше), затем по качественным метрикам.

## Ограничение по расстоянию

- Параметр: `matching.max_distance_km`.
- Значение по умолчанию в конфиге: `30`.
- Изменяется в `config.yaml` без правок кода.

## Особый случай: гидроизоляция

Для `upgrade_category = "Гидроизоляция"`:

- фильтрация идет по `has_hydroisolation=True`,
- предоплата фиксированная (`500`).

## Оплата и подтверждение

- На этапе создания заказа: статус `awaiting_payment`.
- После авто-оплаты: `paid`, партнер получает уведомление.
- Дальнейший поток ведет партнер (`accepted -> in_progress -> ready_for_pickup`).

## Итоговое завершение

Клиент подтверждает финальную оплату:

- заявка переводится в `completed`,
- партнер получает закрывающее уведомление.
