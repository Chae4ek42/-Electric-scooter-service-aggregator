# Модуль: Пользовательский интерфейс и FSM

## Общие принципы навигации

- **Кнопка «Назад»** — на каждом этапе (кроме главного меню) — Inline-кнопка  «Назад», откатывает FSM-состояние на предыдущее. Реализовано для всех состояний, включая `confirm → calendar_time`.
- **Прерывание процедуры** — кнопки «Мои заявки» и «Техподдержка» сбрасывают FSM из любого состояния. Незавершённая заявка **не сохраняется** в БД.
- **Валидация (Pydantic)** — текстовый ввод метро (`MetroTextInput`), названия модели (`ModelNameInput`), бренда (`BrandNameInput`), описания проблемы (`ProblemDescription`) — с русскими сообщениями об ошибках.
- **Catch-all** — запросы в состояниях кнопок отвечают: «Пожалуйста, используйте кнопки».

---

## Схема FSM

```
Оставить заявку
│
├─ service_type: Ремонт | Апгрейд
├─ brand: выбор бренда [→ brand_custom: текстовый ввод бренда]
├─ model: выбор модели [→ model_custom: текстовый ввод]
├─ malfunction_type: Механика | Электрика  (только repair)
├─ upgrade_category: Гидроизоляция | Окраска | Прошивка | Изменение конструкции  (только upgrade)
├─ problem_description: описание проблемы  (все ветки кроме Гидроизоляции)
├─ location_method: ввести метро
├─ metro_search: текстовый ввод станции
├─ metro_confirm: подтверждение
├─ calendar_date: выбор даты
├─ calendar_time: выбор времени  [→ time_fallback если сервисы не работают]
└─ confirm: подтверждение → заглушка оплаты
```

> `specific_problem` удалён. `payment` удалён — pay-хендлеры state-agnostic.
> Добавлены: `brand_custom`, `upgrade_category`, `problem_description`.

## Детальная логика взаимодействия

### 1. Главное меню

Reply-клавиатура:
- **«Оставить заявку»** — запуск FSM
- **«Мои заявки»** — список заявок
- **«Техподдержка»** — ссылка на `SUPPORT_USER`
- **«Панель администратора»** — только для `ADMIN_USERNAMES`

---

### 2. Выбор типа услуги
**Состояние**: `service_type`

Кнопки: **«Ремонт»** / **«Апгрейд»** / Назад.

Callback: `stype:repair` или `stype:upgrade`. Сохраняется в FSM-данные как `service_type`.

---

### 3. Бренд и модель

#### 3.1 Бренд
**Состояние**: `brand`

Inline-сетка 2×2 из брендов БД. Callback: `brand:{id}`. Кнопка «Другой бренд (ввести)» (`brand:other`) — переход в `brand_custom`.

#### 3.1а Кастомный бренд
**Состояние**: `brand_custom`

Текстовый ввод. Pydantic-валидация: `BrandNameInput` (2–100 символов, хотя бы одна буква). После ввода бренда сразу переходит в `model_custom` (текстовый ввод модели).

#### 3.2 Модель
**Состояние**: `model`

Модели подтягиваются по `brand_id`.

- Callback модели: `model:{id}`
- Callback «Другое»: `model:other` → переход в `model_custom`

Pydantic-валидация: `ModelNameInput` (2–50 символов, хотя бы одна буква).

---

### 4. Категория неисправности / апгрейда

#### 4.1 Repair — категория неисправности
**Состояние**: `malfunction_type`

Callback: `malf:Механика` / `malf:Электрика`. Сохраняется как `malfunction_category`. Переход в `problem_description`.

#### 4.2 Upgrade — категория апгрейда
**Состояние**: `upgrade_category`

Кнопки: **Гидроизоляция** / **Окраска** / **Прошивка** / **Изменение конструкции**. Callback: `upcat:{name}`.

- Гидроизоляция — пропуск `problem_description`, сразу в `location_method`
- Окраска / Прошивка / Изменение конструкции — переход в `problem_description`

#### 4.3 Описание проблемы
**Состояние**: `problem_description`

Текстовый ввод с валидацией `ProblemDescription` (3–1000 символов).

Поток:
```
model → malfunction_type → problem_description → location_method  (для repair)
model → upgrade_category → problem_description → location_method  (для upgrade, кроме гидроизоляции)
model → upgrade_category → location_method  (для гидроизоляции)
```

---

### 5. Метро
**Состояния**: `location_method` → `metro_search` → `metro_confirm`

**`location_method`**: единственная кнопка «Ввести станцию метро». (ГЕО заморожен.)

**`metro_search`**: Текстовый ввод. Fuzzy-поиск по 266 станциям:
- Скор > 0.85 или один результат → авто-переход в `metro_confirm`
- Несколько совпадений → Inline-список до 5 вариантов
- Ничего не найдено → предложение ввести точнее

**`metro_confirm`**: кнопки «Да, {station}» / «Искать заново».

Stations хранятся как `metro_station` в FSM-данных.

---

### 6. Календарь и время
**Состояния**: `calendar_date` → `calendar_time`

**`calendar_date`**: динамический календарь. Все даты в **московском времени** (`Europe/Moscow`).
- Сегодня включается, если `текущий_час + 1 < WORK_HOUR_END` (хоть один слот остаётся).
- Далее — следующие `CALENDAR_DAYS` дней (14 по умолчанию).

**`calendar_time`**: часовые слоты. Для сегодняшней даты — отфильтровываются прошедшие слоты. Ближайший доступный — **следующий полный час** (нельзя записаться задним числом). Диапазон: `WORK_HOUR_START`–`WORK_HOUR_END` (08:00–22:00).

Callback времени: `time:HH:MM`.

---

### 7. Автоподбор сервис-центра

Срабатывает в `pick_time` сразу после выбора времени.

```python
ctx = RankingContext(
    service_type=data["service_type"],
    malfunction_category=data["malfunction_category"],
    upgrade_category=data["upgrade_category"],
    user_metro=data["metro_station"],
    scheduled_time=time_str,
)
result = await rank_services(ctx, session, limit=1)
# result: RankingResult(matches, time_fallback, suggested_time)
```

Принцип ранжирования:
- Фильтр `is_available=True`
- Скор `= 0.6 × проксимитет + 0.4 × рейтинг`
- Близость — BFS по графу пересадок (`metro_graph.py`)
- Сортировка по скору, при равенстве — по `yandex_rating` убыванию
- Гидроизоляция: фильтрация по `has_hydroisolation=True` независимо от `service_type`
- Фильтрация по времени работы сервиса (`open_time` / `close_time`)

**Time fallback**: если ни один сервис не работает в выбранное время, пользователю предлагается ближайшее доступное время (кнопка «Записаться на HH:MM») или возможность выбрать другую дату.

Если сервисов нет — пользователь получает сообщение и возвращается в меню.

---

### 8. Подтверждение заявки
**Состояние**: `confirm`

Показывается сводка:

```
Модель: Xiaomi Mi 4 Pro
Метро: Курская
Дата: 08.04.2026
Время: 13:00
Стоимость диагностики: 500 руб.
```

> **Сервис-центр не отображается** до внесения предоплаты.

Кнопки: **«Подтвердить»** / **«Отменить»** (заявка не сохраняется).

При подтверждении:
1. Создаётся `Order` со статусом `awaiting_payment`.
2. Отправляется заглушка предоплаты:

```
🔒 Предоплата
Система предоплаты находится в разработке.
Мы свяжемся с вами для подтверждения записи.
```

---

### 9. Мои заявки
Каждая заявка высылается **отдельным сообщением** (не одним текстовым полотном). Содержимое:

```
*Заявка №2*
  Модель: Kugoo M4 Pro
  Сервис-центр: Motrax Mall
  Дата: 08.04.2026 14:00
  Метро: Курская
  Статус: Ожидает оплаты
```

Для заявок со статусом `awaiting_payment` — inline-кнопки:
- **«Перейти к оплате»** → заглушка
- **«Отменить заявку»** → статус `cancelled`

Статусы заявок:

| Статус DB | Отображение |
|---|---|
| `awaiting_payment` | Ожидает оплаты (сервис-центр скрыт) |
| `accepted` | Принята |
| `interrupted` | Прервана |
| `completed` | Завершена |
| `cancelled` | Отменена |

---

### 10. Панель администратора

Вход: кнопка «Панель администратора» (username в `ADMIN_USERNAMES`).

**Список заявок**: пагинация 10 записей, сортировка по дате, фильтр по статусу.

**Карточка заявки**: ID, дата, пользователь, модель, сервис-центр, метро, дата записи, статус.

**Смена статуса**: кнопки «Принята» / «Прервана» / «Завершена» / «Отменена» с подтверждением `show_alert`.


## Общие принципы навигации
- **Кнопка "Назад"**: На каждом этапе (кроме главного меню) присутствует Inline-кнопка "Назад", которая откатывает FSM-состояние на предыдущее и возвращает пользователю соответствующее меню. ✅ **Реализовано** для всех 12 состояний, включая `confirm → calendar_time`.
- **Прерывание процедуры**: Если пользователь выбирает команду из основного текстового меню (например, "Мои заявки") во время заполнения заявки, текущая процедура принудительно завершается сообщением "Процедура прервана", а состояние сбрасывается. ✅ **Реализовано** — работает из любого состояния, включая `metro_search` (текстовый ввод).
- **Валидация (Pydantic)**: Текстовый ввод метро (`MetroTextInput`), описание проблемы (`ProblemDescription`), название модели (`ModelNameInput`) — с человеческими русскими сообщениями об ошибках. ✅ **Реализовано**.
- **Catch-all**: Произвольный текст в состояниях, ожидающих кнопок, вызывает сообщение «Пожалуйста, используйте кнопки для навигации». ✅ **Реализовано**.

## Детальная логика взаимодействия (UI/UX)

### 1. Точка входа: Главное меню
**Текстовое (Reply) меню**:
- "Оставить заявку" (триггер FSM)
- "Мои заявки" (список заявок: дата, время, причина, модель, статус)
- "Техподдержка" (ссылка на контакт из `.env`)
- "Панель администратора" *(только для пользователей из `ADMIN_IDS`)*

---

### 2. Выбор типа услуги
**Состояние**: `Order.service_type`
- **Кнопки**: "Сделать ремонт", "Сделать апгрейд".
- **Кнопка "Назад"**: Сброс FSM в `None`.

---

### 3. Выбор Бренда и Модели (Полностью Inline)
**Ранее ожидался текстовый ввод, теперь — двухуровневое Inline-меню.**

#### 3.1 Выбор Бренда
**Состояние**: `Order.brand`
- **Источник**: Данные подтягиваются из таблицы `brands` в БД.
- **Примеры**: Kugoo, Xiaomi, Ninebot и др.
- **Кнопка "Назад"**: Возвращает к выбору типа услуги.

#### 3.2 Выбор Модели
**Состояние**: `Order.model`
- **Источник**: Данные подтягиваются из таблицы `models`, связанные с выбранным `brand_id`.
- **Кнопка "Другое (ввести вручную)"**: переводит в состояние `model_custom` для ручного ввода названия. Ввод проверяется через `ModelNameInput`.
- **Действие**: После выбора конкретной модели переход к выбору неисправности.
- **Кнопка "Назад"**: Возвращает к выбору бренда.

---

### 4. Ветка "Ремонт" (Repair Journey)
**Состояние**: `Order.malfunction_type`
- **Меню**: Выбор группы (Механика/Электрика).
- **Кнопка "Назад"**: Возвращает к выбору модели.

#### 4.1 Конкретные проблемы
**Состояние**: `Order.specific_problem`
- **Источник**: Данные из таблицы `services` (связаны с `service_type` и `category`).
- **Кнопка "Назад"**: Возвращает к выбору группы (2.1).

---

### 5. Локация и Метро
**Состояние**: `Order.location_method` → `Order.metro_search` → `Order.metro_confirm`
- **Интерфейс**: Inline-кнопки "Отправить геопозицию" и "Ввести станцию метро".
- **Геопозиция**: Принимается на мобильных. На десктоп-версии TG отправка недоступна: бот показывает сообщение с кнопками "Ввести станцию метро" и "Назад" (inline-клавиатура остаётся видной).
- **Текстовый ввод**: Нечёткий поиск (fuzzy-match) по 266 станциям метро Москвы. При множественных совпадениях — Inline-список до 5 вариантов.
- **Кнопка "Назад"**: Возвращает к выбору проблемы.
- См. подробности в [03_METRO_SEARCH.md](03_METRO_SEARCH.md).

---

### 6. Календарь и время
**Состояние**: `Order.calendar_date` → `Order.calendar_time`
- Динамический календарь на 14 дней (со следующего дня).
- Тайм-слоты с 10:00 до 20:00, шаг 1 час.
- См. подробности в [05_CALENDAR.md](05_CALENDAR.md).

---

### 7. Подтверждение заявки
**Состояние**: `Order.confirm`
- Отображается сводка: модель, услуга, метро, дата, время.
- Кнопки: "Подтвердить" / "Отменить".
- При подтверждении — заявка сохраняется в БД со статусом `awaiting_payment`, переход к экрану оплаты.
- "Назад" → возврат к выбору времени.

---

### 8. Оплата (стаб)
**Состояние**: `Order.payment`
- Отображается: "Заявка №X создана. Для подтверждения необходимо внести предоплату."
- **Кнопка "Перейти к оплате"**: стаб — сообщает "Система оплаты в разработке".
- **Кнопка "Отменить заявку"**: переводит статус заявки в `cancelled`.

---

### 9. Мои заявки и Поддержка
- **Мои заявки**: Выводит список заявок текущего пользователя. Данные агрегируются из таблиц `orders`, `services`, `models`.
- **Поддержка**: Ссылка на аккаунт техподдержки, указанный в `SUPPORT_USER` (окружение).

---

### 10. Панель администратора (только для ADMIN_IDS)

**Вход**: Кнопка «Панель администратора» в главном меню (видна только администраторам).

**Главный экран**: Статистика заявок по статусам + кнопки навигации.

**Список заявок**:
- Пагинация (10 записей/страницу), сортировка по дате создания.
- Фильтр по статусу через отдельное меню.
- Каждая строка: `#ID • ДД.ММ.ГГГГ • [статус]`.

**Карточка заявки** — полная информация:
- ID и дата создания
- Пользователь: имя, @username, Telegram ID
- Модель: бренд + название (или ручной ввод)
- Услуга: название, тип, категория
- Метро, дата и время записи
- Статус (с кнопками смены)
- ID платежа (если есть)
- Описание проблемы (если есть)

**Смена статуса**: кнопки «Принята», «Прервана», «Завершена», «Отменена» с подтверждением через `show_alert`.
