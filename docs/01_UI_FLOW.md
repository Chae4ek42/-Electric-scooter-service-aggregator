# UI Flow

## 1. Клиентский поток

1. Пользователь запускает "Оставить заявку".
2. Выбирает тип услуги, бренд/модель, категорию проблемы.
3. Указывает метро и время визита.
4. Система ранжирует сервисы и выбирает лучший матч.
5. Если выбранный слот недоступен, предлагаются несколько ближайших доступных слотов (дата+время) или возврат к выбору даты.
6. Пользователь подтверждает заявку.
7. После оплаты заявка уходит партнёру.

## 2. Поток партнёра

1. Партнёр заполняет анкету (`ServiceDraft`).
2. На шаге подтверждения анкеты доступна кнопка `Назад`, чтобы вернуться к редактированию перед отправкой на модерацию.
3. Администратор одобряет или отклоняет.
4. После одобрения партнёр работает с заявками:
    - принимает/отклоняет,
    - формирует смету,
    - при указании итоговой стоимости сначала вводит текст сметы,
    - затем вводит итоговую сумму,
    - клиент получает кнопку оплаты (mock) и завершает заказ.
5. В `Редактировать профиль` активный партнёр попадает в draft-редактор с теми же правилами валидации, что и при первичном заполнении (включая зависимые шаги: `Гидроизоляция -> цена`, `Диагностика -> входит в стоимость`).
6. Изменения профиля применяются без ремодерации: статус остаётся `активный`, админам уходит уведомление об изменённом поле.

## 3. Админские потоки

- Клиентский админ-модуль: контроль заказов, фильтры по статусам.
- Партнёрский админ-модуль: модерация анкет (`ожидает/активный/приостановлен/отклонён`).

## 4. Ключевые UX-инварианты

- В каждой форме есть путь назад и безопасный выход в меню.
- При прерывании форма не ломает данные; прогресс анкеты хранится в `ServiceDraft`.
- Для сложных шагов используются явные подтверждения (метро, смета, финальная оплата).
- В текстах UI названия полей выводятся без одинарных кавычек.

## 5. Логика оплаты на уровне UI

- На старте заказа берётся предоплата.
- Для гидроизоляции предоплата фиксирована (`500`).
- Для остальных сценариев предоплата берётся из `diagnostics_price`.
- Перед финальным завершением показывается остаток к оплате.
- Расчёты выполняются централизованно через `PaymentPolicy` (без дублирования формул в хендлерах).
- Финальная оплата в текущем контуре остаётся mock-сценарием (без подключения реального платёжного адаптера).
