# UI Flow

## 1. Клиентский поток

1. Пользователь запускает "Оставить заявку".
2. На старте формы выбирает город (fuzzy-поиск и подтверждение выбранного варианта).
3. Выбирает тип услуги, бренд/модель, категорию проблемы.
4. Для Москвы указывает метро. Для других городов указывает адрес (адрес геокодируется, при неудаче бот просит уточнить адрес до улицы/дома/корпуса).
5. Выбирает время визита.
6. Система ранжирует сервисы и выбирает лучший матч.
7. Если выбранный слот недоступен, предлагаются несколько ближайших доступных слотов (дата+время) или возврат к выбору даты.
8. Пользователь подтверждает заявку.
9. При создании присваивается уникальный 6-значный код заказа; код показывается клиенту и партнёру.
10. После оплаты заявка уходит партнёру.

## 2. Поток партнёра

1. Партнёр заполняет анкету (`ServiceDraft`) в режиме city-first (с подтверждением города).
2. Для Москвы заполняются адрес и метро; для других городов метро не запрашивается.
3. На шаге подтверждения анкеты доступна кнопка `Назад`, чтобы вернуться к редактированию перед отправкой на модерацию.
4. Перед отправкой анкеты проверяется геокодирование адреса: без координат отправка блокируется, бот просит уточнить адрес (и метро для Москвы).
5. Администратор одобряет или отклоняет.
6. После одобрения партнёр работает с заявками:
    - принимает/отклоняет,
    - формирует смету,
    - при указании итоговой стоимости сначала вводит текст сметы,
    - затем вводит итоговую сумму,
    - клиент получает кнопку оплаты (mock) и завершает заказ.
7. В `Редактировать профиль` активный партнёр попадает в draft-редактор с теми же правилами валидации, что и при первичном заполнении (включая зависимые шаги: `Гидроизоляция -> цена`, `Диагностика -> входит в стоимость`).
8. Изменения профиля применяются без ремодерации: статус остаётся `активный`, админам уходит уведомление об изменённом поле.
9. В pending-режиме `Продолжить заполнение` показывает следующий релевантный шаг, а `Изменить анкету` отображает только уже начатые поля.

## 3. Админские потоки

- Клиентский админ-модуль: контроль заказов, фильтры по статусам.
- Клиентский админ-модуль в карточке заявки больше не показывает inline-кнопки смены статуса; вместо этого есть переход `К сервису`.
- Партнёрский админ-модуль: модерация анкет (`ожидает/активный/приостановлен/отклонён`) + статистика сервиса с просмотром всех его заявок и детальной карточки каждой заявки.

## 4. Ключевые UX-инварианты

- В каждой форме есть путь назад и безопасный выход в меню.
- При прерывании форма не ломает данные; прогресс анкеты хранится в `ServiceDraft`.
- Для сложных шагов используются явные подтверждения (метро, смета, финальная оплата).
- В текстах UI названия полей выводятся без одинарных кавычек.

## 5. Логика оплаты на уровне UI

- На старте заказа берётся предоплата.
- Для гидроизоляции предоплата фиксирована (`500`).
- Для остальных сценариев предоплата берётся из `diagnostics_price`.
- Перед финальным завершением показывается остаток к оплате.
- Расчёты выполняются централизованно через `PaymentPolicy` (без дублирования формул в хендлерах).
- Финальная оплата в текущем контуре остаётся mock-сценарием (без подключения реального платёжного адаптера).
