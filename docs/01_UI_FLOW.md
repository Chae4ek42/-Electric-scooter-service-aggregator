# Модуль: Пользовательский интерфейс и FSM

## Общие принципы навигации

- **Кнопка «Назад»** — на каждом этапе (кроме главного меню) — Inline-кнопка  «Назад», откатывает FSM-состояние на предыдущее. Реализовано для всех состояний, включая `confirm → calendar_time`.
- **Прерывание процедуры** — кнопки «Мои заявки» и «Поддержка» сбрасывают FSM из любого состояния. Незавершённая заявка **не сохраняется** в БД.
- **Валидация (Pydantic)** — текстовый ввод метро (`MetroTextInput`), названия модели (`ModelNameInput`), бренда (`BrandNameInput`), описания проблемы (`ProblemDescription`) — с русскими сообщениями об ошибках.
- **Catch-all** — запросы в состояниях кнопок отвечают: «Пожалуйста, используйте кнопки».

---

## Схема FSM

```
Оставить заявку
│
├─ service_type: Ремонт | Апгрейд
├─ brand: выбор бренда [→ brand_custom: текстовый ввод бренда]
├─ model: выбор модели [→ model_custom: текстовый ввод]
├─ malfunction_type: Механика | Электрика  (только repair)
├─ upgrade_category: Гидроизоляция | Окраска | Прошивка | Изменение конструкции  (только upgrade)
├─ problem_description: описание проблемы  (все ветки кроме Гидроизоляции)
├─ location_method: ввести метро
├─ metro_search: текстовый ввод станции
├─ metro_confirm: подтверждение
├─ calendar_date: выбор даты
├─ calendar_time: выбор времени  [→ time_fallback если сервисы не работают]
└─ confirm: подтверждение → заглушка оплаты
```

> `specific_problem` удалён. `payment` удалён — pay-хендлеры state-agnostic.
> Добавлены: `brand_custom`, `upgrade_category`, `problem_description`.

## Детальная логика взаимодействия

### 1. Главное меню

Reply-клавиатура:
- **«Оставить заявку»** — запуск FSM
- **«Мои заявки»** — список заявок
- **«Поддержка»** — inline-меню: «Техническая поддержка» (`SUPPORT_USER`), «Вопросы по сотрудничеству» (`COOPERATION_USER`)
- **«Панель администратора»** — только для `ADMIN_USERNAMES`

---

### 2. Выбор типа услуги
**Состояние**: `service_type`

Кнопки: **«Ремонт»** / **«Апгрейд»** / Назад.

Callback: `stype:repair` или `stype:upgrade`. Сохраняется в FSM-данные как `service_type`.

---

### 3. Бренд и модель

#### 3.1 Бренд
**Состояние**: `brand`

Inline-сетка 2×2 из брендов БД. Callback: `brand:{id}`. Кнопка «Другой бренд (ввести)» (`brand:other`) — переход в `brand_custom`.

#### 3.1а Кастомный бренд
**Состояние**: `brand_custom`

Текстовый ввод. Pydantic-валидация: `BrandNameInput` (2–100 символов, хотя бы одна буква). После ввода бренда сразу переходит в `model_custom` (текстовый ввод модели).

#### 3.2 Модель
**Состояние**: `model`

Модели подтягиваются по `brand_id`.

- Callback модели: `model:{id}`
- Callback «Другое»: `model:other` → переход в `model_custom`

Pydantic-валидация: `ModelNameInput` (2–50 символов, хотя бы одна буква).

---

### 4. Категория неисправности / апгрейда

#### 4.1 Repair — категория неисправности
**Состояние**: `malfunction_type`

Callback: `malf:Механика` / `malf:Электрика`. Сохраняется как `malfunction_category`. Переход в `problem_description`.

#### 4.2 Upgrade — категория апгрейда
**Состояние**: `upgrade_category`

Кнопки: **Гидроизоляция** / **Окраска** / **Прошивка** / **Изменение конструкции**. Callback: `upcat:{name}`.

- Гидроизоляция — пропуск `problem_description`, сразу в `location_method`
- Окраска / Прошивка / Изменение конструкции — переход в `problem_description`

#### 4.3 Описание проблемы
**Состояние**: `problem_description`

Текстовый ввод с валидацией `ProblemDescription` (3–1000 символов).

При ошибке валидации бот отвечает сообщением без префикса «Value error»:
```
Описание слишком короткое (минимум 3 символа).
Пожалуйста, опишите вашу проблему подробнее.
```

Поток:
```
model → malfunction_type → problem_description → location_method  (для repair)
model → upgrade_category → problem_description → location_method  (для upgrade, кроме гидроизоляции)
model → upgrade_category → location_method  (для гидроизоляции)
```

---

### 5. Метро
**Состояния**: `location_method` → `metro_search` → `metro_confirm`

**`location_method`**: единственная кнопка «Ввести станцию метро». (ГЕО заморожен.)

**`metro_search`**: Текстовый ввод. Fuzzy-поиск по 266 станциям:
- Скор > 0.85 или один результат → авто-переход в `metro_confirm`
- Несколько совпадений → Inline-список до 5 вариантов
- Ничего не найдено → предложение ввести точнее

**`metro_confirm`**: кнопки «Да, {station}» / «Искать заново».

Stations хранятся как `metro_station` в FSM-данных.

---

### 6. Календарь и время
**Состояния**: `calendar_date` → `calendar_time`

**`calendar_date`**: динамический календарь. Все даты в **московском времени** (`Europe/Moscow`).
- Сегодня включается, если `текущий_час + 1 < WORK_HOUR_END` (хоть один слот остаётся).
- Далее — следующие `CALENDAR_DAYS` дней (14 по умолчанию).

**`calendar_time`**: часовые слоты. Для сегодняшней даты — отфильтровываются прошедшие слоты. Ближайший доступный — **следующий полный час** (нельзя записаться задним числом). Диапазон: `WORK_HOUR_START`–`WORK_HOUR_END` (08:00–22:00).

Callback времени: `time:HH:MM`.

---

### 7. Автоподбор сервис-центра

Срабатывает в `pick_time` сразу после выбора времени.

```python
ctx = RankingContext(
    service_type=data["service_type"],
    malfunction_category=data["malfunction_category"],
    upgrade_category=data["upgrade_category"],
    user_metro=data["metro_station"],
    scheduled_time=time_str,
)
result = await rank_services(ctx, session, limit=1)
# result: RankingResult(matches, time_fallback, suggested_time)
```

Принцип ранжирования:
- Фильтр `is_available=True`
- Скор `= 0.6 × проксимитет + 0.4 × рейтинг`
- Близость — BFS по графу пересадок (`metro_graph.py`)
- Сортировка по скору, при равенстве — по `yandex_rating` убыванию
- Гидроизоляция: фильтрация по `has_hydroisolation=True` независимо от `service_type`
- Фильтрация по времени работы сервиса (`open_time` / `close_time`)

**Time fallback**: если ни один сервис не работает в выбранное время, пользователю предлагается ближайшее доступное время (кнопка «Записаться на HH:MM») или возможность выбрать другую дату.

Если сервисов нет — пользователь получает сообщение и возвращается в меню.

---

### 8. Подтверждение заявки
**Состояние**: `confirm`

Показывается сводка (**без указания сервис-центра** — клиент не должен знать о сервисе до оплаты):

```
Подтвердите заявку:

Модель: Kugoo Kugoo Max Speed
Метро: Сокольники
Дата: 18.04.2026
Время: 10:00
Стоимость диагностики: 1000 руб.
```

**Текст о диагностике** зависит от настроек сервиса:
- `diagnostics_included=True` → «Диагностика входит в стоимость ремонта. Если вы передумали до приезда в сервис — вернём деньги 🤝»
- `diagnostics_included=False` → «В этом сервисе диагностика не входит в стоимость ремонта. Если выполнена только диагностика — деньги не возвращаются. Если передумали до приезда — вернём деньги 🤝»

> **Сервис-центр НЕ отображается** до оплаты.

Кнопки: **«Подтвердить»** / **«Отменить»** (заявка не сохраняется).

При подтверждении:
1. Создаётся `Order` со статусом `awaiting_payment`.
2. Запускается заглушка предоплаты.
3. После успешной оплаты клиенту отправляется полная информация о заявке с данными сервис-центра:

```
✅ Оплата заявки №{id} прошла успешно!

Сервис-центр: {name}
Адрес: {address}
Телефон: {phone}
Модель: {model}
Метро: {metro}
Дата: {date} {time}
```

4. Партнёру отправляется уведомление о новой заявке.

### 9. Мои заявки
Каждая заявка высылается **отдельным сообщением** (не одним текстовым полотном). Содержимое:

```
*Заявка №2*
  Модель: Kugoo M4 Pro
  Сервис-центр: Motrax Mall
  Дата: 08.04.2026 14:00
  Метро: Курская
  Статус: Ожидает оплаты
```

Для заявок со статусом `awaiting_payment` — inline-кнопки:
- **«Перейти к оплате»** → заглушка
- **«Отменить заявку»** → статус `cancelled`

Статусы заявок:

| Статус DB | Отображение |
|---|---|
| `awaiting_payment` | Ожидает оплаты (сервис-центр скрыт) |
| `paid` | Оплачено |
| `accepted` | Принята |
| `in_progress` | В работе |
| `ready_for_pickup` | Готов к выдаче |
| `completed` | Завершена |
| `interrupted` | Прервана |
| `cancelled` | Отменена |
| `rejected_by_partner` | Отклонена партнёром |
| `client_refused` | Клиент отказался |
| `disputed` | Оспорена |
| `no_center` | Не найден центр (service\_id = NULL) |

> **Черновики:** заявки в `awaiting_payment` скрыты в списке заявок админки по умолчанию (доступны через фильтр «Ожид. оплаты»).

### 10a. Жизненный цикл заявки после предоплаты

```
awaiting_payment
       ▼
   accepted                ← партнёр принял заявку
   ╱        ╲
  ▼          ▼
client_refused    start_work (партнёр нажал «Принять в работу»)
  │                    │
  │           заполняет смету:
  │           cost → items → deadline → description(опц.) → confirm
  │                    │
  │                    ▼
  │              in_progress        ← клиент получает уведомление со сметой
  │              (клиент подтверждает или отклоняет смету)
  │                    │
  │                    ▼
  │            ready_for_pickup     ← партнёр нажал «Готов к выдаче»
  │              ╱         ╲
  │             ▼           ▼
  │        completed     disputed
  │        (оплата)    (клиент оспорил → админ уведомлён)
```

#### Действия партнёра (partner-bot)

| Действие | Статус заявки | Кнопка | Результат |
|---|---|---|---|
| Принять в работу | `accepted` | «Принять в работу» | FSM сметы → `in_progress` |
| Клиент отказался | `accepted` | «Клиент отказался» | FSM причины → `client_refused` |
| Готов к выдаче | `in_progress` | «Готов к выдаче» | → `ready_for_pickup` |
| Указать стоимость | `accepted`, `in_progress` | «Указать итоговую стоимость» | Ввод `total_cost` |

#### FSM сметы (PartnerOrderFSM)

```
estimate_cost → estimate_items → estimate_deadline → estimate_description (опц.) → estimate_confirm
```

При подтверждении сметы: статус → `in_progress`, клиент получает уведомление с деталями сметы и кнопками «Подтвердить смету» / «Отклонить».

#### Действия клиента (client-bot)

| Действие | Когда | Кнопки | Результат |
|---|---|---|---|
| Были ли в сервисе? | После `client_refused` | Да / Нет | Записывается `client_visited` |
| Подтвердить смету | После получения сметы (`in_progress`) | Подтвердить / Отклонить | `client_confirmed_estimate` |
| Оплатить | `ready_for_pickup` | Оплатить и завершить | → `completed` (заглушка) |
| Оспорить | `ready_for_pickup` | Оспорить | FSM причины → `disputed`, уведомление админам |

### 10. Панель администратора (клиентский бот)

Вход: кнопка «Панель администратора» (username в `ADMIN_USERNAMES`).

**Главное меню**: статистика по статусам, кнопки «Все заявки», «Заявки по статусу», «Заявки партнёров».

**Список заявок**: пагинация 10 записей, сортировка по дате, фильтр по статусу. Заголовок: `Все заявки: N (стр. X/Y)`.

**Карточка заявки**: ID, дата, пользователь, модель, сервис-центр, метро, дата записи, статус, диагностика, смета.

**Смена статуса**: кнопки «Принята» / «Прервана» / «Завершена» / «Отменена» с подтверждением `show_alert`.

**Заявки партнёров** (`adm:partners:{page}`): пагинация 10, отображает все `ServiceOwner` записи. Заголовок: `Заявки партнёров: N (стр. X/Y)`. Карточка — только для чтения (навигация «К списку» / «В главное меню»).

> Управление партнёрами (одобрение, отклонение, приостановка) вынесено в партнёрский бот — см. [05_PARTNER_BOT.md](05_PARTNER_BOT.md).
